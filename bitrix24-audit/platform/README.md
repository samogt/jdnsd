# Битрикс24 · Путь сотрудника — 2.0.0

**[Скачать готовое приложение для Windows](https://github.com/samogt/jdnsd/raw/refs/heads/main/bitrix24-audit/bitrix24_gui.zip)** · [Проверки и сборка Windows](https://github.com/samogt/jdnsd/actions/workflows/platform-v2-tests.yml)

Это новое приложение с постоянной очередью запросов. Последовательный PowerShell-сборщик 1.x больше не используется в готовом архиве.

## Запуск

1. Скачайте и полностью распакуйте архив в новую папку Windows 10/11 x64.
2. Дважды нажмите **START_GUI.cmd**. Откроется локальная страница в обычном браузере.
3. Введите вебхук и нажмите **«Проверить вебхук»**. Показаны владелец URL, ответы `profile`, фактический `scope` без `full:true` и выбранный пользователь, если его ID уже введён.
4. Загрузите список сотрудников или введите ID. По умолчанию сотрудник не выбран. Период установлен на последние два календарных месяца.
5. Выберите источники и начните сбор. Хронология доступна во время работы. CSV и полный ZIP-отчёт можно получить в любой момент.

Python, SQLite и сервер устанавливать не требуется: официальный переносимый Python включён в архив. Приложение работает только на `127.0.0.1` с локальным ключом сессии. Облачного сервера приложения нет. Окно запуска остаётся открытым; штатное завершение — кнопка **«Завершить приложение»** в браузере. Повторный запуск открывает уже работающий экземпляр.

## Что изменилось в архитектуре

- Каждый источник имеет собственную сохраняемую очередь. Длинный Диск, CRM или задачи не удерживают весь сбор. Планировщик поочерёдно выдаёт работу готовым источникам, максимум три сетевых операции одновременно и один новый HTTP-вызов в секунду для реального портала.
- Следующая страница и дочерние объекты записываются в SQLite в одной транзакции с обработкой ответа. После перезапуска продолжаются конкретные недочитанные запросы; завершённые страницы не перечитываются для восстановления места обхода.
- Истории задач, трудозатраты, содержимое папок и комментарии объединяются в штатные REST-пакеты до 25 команд. Каждый ответ и ошибка обрабатываются отдельно. Недоступный пакетный метод имеет обычный резервный вызов.
- HTTP 429 и `Retry-After` откладывают запросы с сохранением срока. Временный отказ одного метода не превращается в ожидание перед всем сбором. Глобальный `QUERY_LIMIT_EXCEEDED` соблюдается. Постоянные отказы показываются с кодом API и ответом.
- Можно приостановить весь сбор или один источник. Полученные строки и очередь сохраняются. Отчёт явно показывает незавершённые, недоступные и ошибочные источники.
- Профиль и выданные scopes проверяются отдельно от объектных прав. `user.get` подтверждает выбранного пользователя; он не даёт прав читать задачи, CRM или Диск другого человека.

Вебхук сохраняется только в памяти. После перезапуска для продолжения нужно снова ввести вебхук того же портала и владельца. SQLite, ответы и отчёты по умолчанию находятся в `%LOCALAPPDATA%\Bitrix24_Platform`; путь показан в разделе сохранённых выгрузок. Секреты известных webhook-URL и auth-полей маскируются в сохраняемых ответах. Файлы содержат персональные и рабочие данные, доступные владельцу вебхука.

## Какие данные собираются

| Источник | Запросы и смысл данных |
| --- | --- |
| Журнал событий | `main.eventlog.list`, сотрудник и диапазон дат; зависит от тарифа и хранения журнала |
| Задачи | Приоритетно связанные с сотрудником задачи, затем все доступные; `tasks.task.history.list` с проверкой `user.id`; целая история принимается без выдуманной пагинации |
| Трудозатраты | `task.elapseditem.getlist`, пять позиционных параметров, отбор по `USER_ID`; даты ручного учёта не выдаются за точное время физической работы |
| CRM-дела | Автор создания и последний редактор, серверные фильтры сотрудника и дат |
| CRM и комментарии | Сначала авторство метаданных за период, затем доступные родительские карточки для комментариев в чужих и старых объектах; лиды, сделки, контакты, компании, предложения, счета и обнаруженные смарт-процессы |
| Диск | Проверка допустимых полей фильтра, личное хранилище в приоритете, затем доступные общие хранилища и папки; только метаданные создания, последнего изменения и корзины |
| Контроль времени | Месячные отчёты рабочего времени и записи приложения при наличии прав и включённой функции |
| Рабочее время | Интервалы `timeman.record.list`, их начало и окончание; записи могут корректироваться |
| Телефония | Звонки сотрудника, дата, результат и длительность; без загрузки аудио |
| Шаблоны БП | Пользователь и дата последнего создания или изменения доступного шаблона; снимок, а не история настройки роботов |

Для всех перечисленных источников нужны scopes `main`, `task`, `crm`, `disk`, `timeman`, `telephony`, `bizproc`. Для списка сотрудников — один из `user`, `user_basic`, `user_brief`. Отсутствующие scopes показываются, а соответствующие источники не вызываются.

**Границы полноты:** REST не предоставляет единого запроса ко всем действиям человека. Скрытые и удалённые объекты, несохранённые журналы, промежуточные изменения метаданных, клики и чтение карточек задним числом не восстанавливаются. Чаты, календарь, лента, история изменения прав и работа роботов отдельными коллекторами здесь не охвачены. Наличие доступа к этим модулям не означает, что их история вошла в отчёт. `done` означает завершение реализованного обхода доступных данных, а не подтверждение полной истории портала. Изменения портала во время долгого обхода могут менять выборку; транзакционного снимка портал не даёт.

Таблица разделяет **исторические события**, **учётные записи**, **снимки метаданных** и **косвенные признаки**. Каждая строка проверяется по выбранному автору и периоду и ссылается на фактический ответ API. События разных источников могут описывать одно действие; они не склеиваются предположением.

## Запросы по вебхуку

Раздел **«Запросы API»** выполняет один явный вызов: метод чтения, версия REST 2/3 и параметры JSON. Есть примеры с выбранным сотрудником. Показаны HTTP-статус, параметры и ответ API; следующие страницы не загружаются автоматически. Изменяющие данные методы и произвольный `batch` в этом разделе не выполняются.

## Уже скачанные данные 1.x

В разделе сохранённых выгрузок откройте **«Импортировать уже скачанные ответы версии 1.x»**, укажите старую папку с `manifest.json`, введите прежний вебхук и импортируйте. Поддерживается формат 2 старого manifest и московский/UTC часовой пояс. Совместимые успешные ответы используются локально; авторизация проверяется заново. Старые файлы не изменяются. Страницы с другими параметрами могут потребовать новых запросов: неполная широкая страница не выдаётся за полный результат другого фильтра.

## Проверка реализации

Автоматические проверки включают контракты методов, 130 записей истории одним ответом, авторов и даты, комментарии в чужих карточках, ошибки внутри пакета, большой Диск, независимое завершение остальных источников, сохранение очереди и точное продолжение после перезапуска, импорт 1.x, scope, HTTP 401/429, прерывание HTTP после получения заголовков, защиту локальной сессии и экспорт с первоисточниками.

Windows-сборка тестирует распакованный архив вместе с включённым runtime в настоящем Microsoft Edge: подключение, выбор сотрудника, отчёт во время большой очереди, паузу одного источника, CSV, одиночный API-вызов, перезапуск и продолжение. Используются синтетические данные и локальный HTTP-сервер. Рабочий вебхук пользовательского портала в CI не передаётся.

Сборка публикует ZIP только после этих проверок. `build_manifest.json` внутри архива фиксирует исходный коммит, официальный runtime и хеши файлов. Python распространяется с его лицензией в `.runtime`.
