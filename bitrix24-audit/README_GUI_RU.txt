ВЕРСИЯ 1.6.0 — пакетный сбор, совместимость Windows PowerShell 5.1

БИТРИКС24 — ОТЧЁТ ПО ВЫБРАННОМУ СОТРУДНИКУ

ЗАПУСК
Распакуйте весь архив в обычную папку Windows и дважды нажмите START_GUI.cmd.
Сервер, Python, Node.js, Excel и сторонние модули устанавливать не нужно.
Используются штатные Windows PowerShell 5.1 и WPF.
Не запускайте приложение прямо из окна ZIP: все файлы должны лежать рядом.

СЦЕНАРИЙ РАБОТЫ: ПАРАМЕТРЫ → ФОРМИРОВАНИЕ → ГОТОВЫЙ РЕЗУЛЬТАТ

1. ЗАПОЛНИТЕ ПАРАМЕТРЫ

Входящий вебхук *
Вставьте рабочий HTTPS-адрес вебхука вашего портала:
https://portal.bitrix24.ru/rest/USER_ID/TOKEN/
Принимаются также окончание profile.json и вариант /rest/api/USER_ID/TOKEN/.
Ввод скрыт. Флажок «Показать адрес» позволяет проверить вставленный URL.

Сотрудник *
НИКТО НЕ ВЫБРАН ПО УМОЛЧАНИЮ.
Нажмите «Загрузить список сотрудников», затем выберите человека в списке.
Список содержит ФИО и ID; можно набирать начало фамилии. Уволенные сотрудники
также загружаются, если видимы владельцу вебхука. При доступном статусе они
помечаются в списке.
Первый сотрудник после загрузки автоматически не выбирается.

Для списка нужен scope user, user_basic или user_brief. Если список недоступен,
можно вручную ввести числовой ID нужного человека. Введённый вручную ID без
доступа к справочнику не проверяется на существование: проверьте его по порталу.
При смене вебхука выбор очищается, чтобы не использовать ID другого портала.

Период событий *
Выберите даты в календарях и время ЧЧ:ММ:СС.
При открытии окна стоят последние два календарных месяца. Кнопка
«Последние 2 месяца» обновляет период относительно текущего времени.
Начало включается; отметка окончания НЕ включается. Чтобы включить целый
последний день, укажите 00:00:00 следующего дня в поле «До».

Часовой пояс
По умолчанию — Москва, UTC+03:00. Можно выбрать другой пояс для границ
периода и отображения дат в готовом отчёте.

Куда сохранить отчёт *
Выберите существующую папку. Внутри будет создана отдельная папка выгрузки.
Уже существующие отчёты новый сбор не перезаписывает.

Дополнительные параметры
• Пояс исходных дат без UTC-смещения — Москва; поменяйте, если портал выдаёт
  локальные даты другого пояса.
• Часов в рабочем дне — 8, для отчёта контроля времени.
• Пауза запросов — 550 мс.
• Попыток при временной ошибке — 4.

Нажмите «Сформировать отчёт». Если обязательные поля не заполнены или
значения неверны, приложение попросит их исправить и останется на первом
экране. Без явно выбранного сотрудника сбор не запускается.

2. ДОЖДИТЕСЬ ФОРМИРОВАНИЯ

Приложение автоматически переходит на экран обработки. На нём видны
состояния источников, ошибки и индикатор работы. Параметры заблокированы
до завершения, чтобы характеристики отчёта не менялись в процессе.
Технический журнал раскрывается по желанию.

Процент не вычисляется: общий объём задач, карточек и комментариев заранее
неизвестен. Окно остаётся доступным. На большом портале сбор может быть долгим.

«Остановить и сохранить» заканчивает текущий запрос и сохраняет частичный
отчёт. Ожидание сетевого запроса может занять до 90 секунд. При закрытии окна
во время работы выполняется та же остановка, затем окно закрывается.

3. ПОЛУЧИТЕ ГОТОВЫЙ РЕЗУЛЬТАТ

После завершения автоматически открывается итоговый экран:
• сотрудник и его ID;
• фактические границы периода и часовой пояс;
• число найденных событий и ошибок;
• расположение файлов;
• кнопки «Открыть готовый отчёт», «Открыть файл для Excel», «Папка результатов».

Основной отчёт — HTML-таблица с поиском: дата, время, действие, объект,
тип подтверждения, подробности и ссылки на сохранённый JSON.
Файл CSV открывается в приложении, связанном с CSV в вашей Windows;
при наличии Excel его можно открыть или импортировать туда.

Если часть источников недоступна, выводится «Отчёт готов, есть пробелы».
Если работа остановлена, результат прямо помечается как частичный.
Отсутствующие данные не подменяются вымышленными событиями.

«Настроить другой отчёт» возвращает к заполнению полей. Сотрудника нужно
выбрать заново; предыдущий пользователь автоматически не подставляется.

ПРОДОЛЖЕНИЕ И ПЕРЕСБОРКА
На первом экране можно выбрать другой режим:

«Продолжить ранее начатый сбор»
Выберите папку конкретной выгрузки с manifest.json. Сотрудник, период и пояса
загрузятся из неё и будут заблокированы для изменения. Нужен вебхук того же
портала и владельца. Сохранённые страницы повторно не запрашиваются.

«Пересобрать сохранённый отчёт без интернета»
Выберите папку с manifest.json. Вебхук не нужен, сеть не используется.
Недостающие страницы будут отмечены как пробелы.
Для актуального нового снимка выбирайте «Создать новый отчёт».

ПРАВА И ПОЛНОТА
Для источников сбора нужны scopes:
main, task, crm, disk, timeman, telephony, bizproc.
Для выпадающего списка сотрудников дополнительно нужен один из scopes:
user, user_basic или user_brief.

Права владельца вебхука ограничивают доступные данные. Администратор
Битрикс24 видит больше, но это не восстанавливает очищенные журналы,
безвозвратно удалённые объекты и отсутствующую историю изменений.
Права администратора Windows для приложения не нужны.

Собираются Event Log, история задач, трудозатраты, CRM-дела, элементы
и комментарии CRM, логи приложений, метаданные Диска, рабочее время,
контроль времени, телефония, шаблоны бизнес-процессов.
Подробности источников и документация — в README_COLLECTOR_RU.md.

ФАЙЛЫ ОТЧЁТА
• timeline.html — основная таблица.
• timeline_employee_ID.csv — таблица для Excel.
• timeline_employee_ID.json — структурированные события.
• summary.json и status.json — характеристики и статусы источников.
• collection_errors.json и rejected.json — ошибки и неразобранные даты.
• raw — страницы API и checkpoint для продолжения.
• gui_run.log — журнал окна при завершении процесса; ограничен по объёму.

ID в имени файла заменяется выбранным идентификатором сотрудника.
Вебхук не сохраняется в настройках и не включается в командную строку:
он передаётся дочернему процессу через его окружение. После завершения
отчёта поле вебхука очищается. Известные URL вебхуков и query-токены
маскируются в журнале. Список сотрудников загружается через временный
файл с ID и именами; после чтения файла приложением он удаляется.
Интерфейс и сборщик не меняют данные и права портала.

ПРОВЕРКА БЕЗ ПОРТАЛА
В PowerShell из папки приложения:
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\bitrix24_gui.ps1 -SelfTest

Проверены: ввод и даты, отсутствие сотрудника по умолчанию, выбор человека,
пагинация списка (включая уволенных), маскирование, передача параметров,
реальный дочерний процесс на синтетических ответах, остановка с частичным
отчётом, параметры продолжения и режима без сети.

Проверки выполнены на Windows PowerShell 5.1 и PowerShell 7.4.13 на Linux.
На Windows проверены реальный дочерний процесс, список сотрудников,
создание и отрисовка WPF-окна, обработка HTTP 400/401/429, отмена,
восстановление, история и пакетное чтение. Используются тестовые данные
и локальный HTTP-сервер, без подключения к пользовательскому порталу.
Результаты: https://github.com/samogt/jdnsd/actions/workflows/bitrix24-audit-tests.yml

ИЗМЕНЕНИЯ 1.1.0
• Общий штатный HttpClient вместо Invoke-WebRequest: тело ответа сохраняется при 400/401/403.
• Даты запросов Event Log без дробных секунд, по формату документации.
• При отклонении фильтра дат — однократный переход на фильтр сотрудника и локальный отбор периода. Это может быть дольше и сохранять сырые записи за пределами периода.
• Постоянный отказ источника не повторяется для каждого дня.
• При нуле событий и ошибках окно прямо сообщает, что события не получены.
• Добавлен обязательный файл bitrix24_http.ps1; распакуйте весь новый архив в отдельную папку.
• Проверены реальные ответы тестового HTTP-сервера 400/401, JSON и HTML.

Причину старого HTTP401 нельзя восстановить из присланного текстового журнала: там нет тела ответа. Новая версия раскрывает ответ сервера; недостаточные права или недействующий токен исправляются на портале. Подключение к вашему порталу не проверялось.


Версия 1.2.0 — ограничения API
HTTP429 и RATELIMITEXCEPTION откладывают источник сразу; оставшиеся источники продолжают сбор. После первого обхода выполняется не более одного повторного обхода отложенных источников. При отсутствии Retry-After используется пауза 5 минут; при наличии заголовка приложение не обращается к методу раньше указанного срока. Ожидание перед финальными повторами ограничено общим бюджетом 5 минут. Если требуется больше, формируется частичный отчёт, источник остаётся отложенным: повторите через режим продолжения позднее.
Пауза по умолчанию — 1000 мс. Отсчёт ожидания виден в журнале и в окне; остановка доступна каждую секунду. SQL-таймаут REST3 не повторяет тяжёлый запрос четыре раза перед уменьшением интервала. Блокировку сервера приложение не обходит.
rate_limits.json сохраняет сроки блокировки методов для продолжения. summary.Errors отражает ошибки итоговых статусов, ErrorHistoryCount — все ошибки попыток, в том числе восстановленных источников.
Для проверки без портала запустите TEST_RATE_LIMITS.ps1 в PowerShell. Тест проверяет 429, переход к другим источникам, Retry-After, повтор и остановку без реального ожидания 5 минут.


Версия 1.3.0 — проверка фактических прав и видимое продвижение
Перед обходом вызывается scope без full:true, сохраняется access_check.json с фактическими правами, доменом, владельцем и отсутствующими кодами. Для задач требуется именно task, а не tasks. При выданном task выполняется проба первой страницы tasks.task.list до долгого обхода. Источники без требуемого scope не запрашиваются; приложение не может выдать токену недостающие права.
В 1.6.0 Event Log выполняется перед задачами; задачи обрабатываются последними. Сначала собираются CRM-дела и другие более быстрые источники; полный обход комментариев CRM остаётся длительным на большом портале и показывает текущие вызовы и счётчик событий. После каждого источника сохраняются промежуточные HTML/CSV/JSON. До завершения процесса это частичный результат.
TEST_ACCESS.ps1 проверяет свежесть scope, различие task/tasks, пропуск недоступного источника, продолжение доступного и промежуточный отчёт.
Если права менялись в настройках, сохраните вебхук и заново скопируйте адрес именно отредактированного вебхука. Выполнение scope с full:true показывает все права портала и не доказывает их наличие у используемого токена.
Документация: https://apidocs.bitrix24.ru/api-reference/common/system/scope.html и https://apidocs.bitrix24.ru/api-reference/tasks/tasks-task-list.html


Версия 1.4.0 — результаты и объяснение отбора
История tasks.task.history.list читается одним ответом без выдуманного start. Если сервер явно возвращает next, используется только этот указатель. Массив из 50, 130 или большего количества записей сам по себе не является признаком следующей страницы. Это устраняет ошибочные повторные запросы при получении полной истории.
Задачи читаются от недавно изменённых к старым, без исключения старых задач или задач других ответственных.
diagnosis.json и раздел «Почему найдены именно эти события» в HTML показывают количество прочитанных уникальных записей истории, нераспознанных авторов и дат, записей выбранного сотрудника, попаданий в период и записей вне периода; диапазон прочитанных дат и число записей по ID авторов. Число HTTP-запросов не считается числом действий сотрудника. Диагноз относится только к прочитанной части, а не к неизвестной истории всего портала.
Для локального разбора уже загруженных ответов выберите в окне «Пересобрать сохранённый отчёт без интернета» и старую папку с manifest.json. Первые страницы истории старых версий совместимы с новым читателем. Уже сохранённые JSON повторно не запрашиваются; отсутствующие страницы отмечаются как пробелы. Полное повторное скачивание не требуется.
TEST_HISTORY.ps1 проверяет один ответ со 130 событиями, отбор по автору и периоду, дубликаты, неразобранные даты, частичный диагноз и повторное использование старого кэша без сети.
Повторный разбор не создаёт отсутствующие данные. Для новых данных используйте продолжение сбора; для свежего снимка — новый отчёт. Клики, просмотры и недоступная административная история не восстанавливаются через историю задач.
Документация: https://apidocs.bitrix24.ru/api-reference/tasks/tasks-task-history-list.html

## Версия 1.5.0 — скорость и проверка запуска

Истории задач загружаются через штатный REST `batch` пакетами до 25 задач. Каждая успешная история сохраняется отдельно и сразу доступна для продолжения/пересборки. Ошибка одного ответа не уничтожает соседние: неуспешные истории проверяются отдельными запросами. Если batch недоступен, применяется обычное чтение.

Сначала проверяются задачи, где выбранный сотрудник — постановщик, исполнитель, автор последнего изменения статуса, соисполнитель или наблюдатель. Затем выполняется общий обход всех доступных задач с устранением повторов. Связь с задачей определяет приоритет, а действие в отчёт попадает только после проверки автора и даты. Нет ограничения только назначенными на сотрудника задачами.

Дочерний процесс выводит обычный UTF-8 текст вместо CLIXML. Служебные сообщения загрузки модулей отключены до первой команды. `TEST_BATCH.ps1` проверяет приоритеты и полный обход, 100 историй за четыре HTTP-запроса, сохранение отдельных историй, продолжение без сети и восстановление после ошибки внутри пакета.

Автоматизация Windows: `.github/workflows/bitrix24-audit-tests.yml` запускает проверки на Windows PowerShell 5.1, создаёт настоящее WPF-окно через `-UiSmokeTest` и сохраняет его изображение. Подключение к реальному порталу требует введённого локально вебхука и не является частью синтетических тестов.

В Windows PowerShell 5.1 исправлено чтение JSON-массивов списка сотрудников.
При пакетном чтении задач промежуточная таблица обновляется по мере обхода страниц.
Статус выполняемого источника сохраняется как «Выполняется» до завершения или отмены.

ВЕРСИЯ 1.6.0 — УПРАВЛЕНИЕ ДЛИТЕЛЬНЫМ ОБХОДОМ
Остальные источники выполняются до этапа «Задачи». История и трудозатраты читаются за один проход по задачам. Общая проба tasks.task.list при проверке доступа убрана.
«Открыть текущий отчёт» доступно во время сбора после первого сохранения таблицы.
«Пропустить этот источник» прерывает только текущий этап, сохраняет данные и продолжает остальные. При этом итог помечается как частичный, даже если технических ошибок нет.
«Остановить и сохранить» завершает весь сбор с частичным отчётом. Ожидающий HTTP-запрос прерывается, а не ожидает 90-секундного таймаута. Намеренный пропуск не повторяется автоматически в текущем запуске.
Для недостающих данных выберите продолжение и ту же папку: успешные страницы не скачиваются заново. Сотрудник и период берутся из прежнего manifest.json.
В окне показываются проверенные задачи, общее число (если известно), записи истории и длительность ожидания текущего запроса. Срок ожидания увеличивается даже без новых строк журнала. Эти показатели также есть в run_state.json.
Новые проверки: TEST_LARGE_PORTAL.ps1 (10000 задач, 8000 записей чужого автора), TEST_CONTROLS.ps1 (пропуск и таймер), TEST_HTTP.py (остановка и пропуск во время реального задержанного HTTP-запроса).
