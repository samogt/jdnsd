# Хронология сотрудника Битрикс24 за последние два месяца

Сотрудник **выбирается явно в интерфейсе** или передаётся через `-EmployeeId` при консольном запуске. Сотрудника по умолчанию нет. Период по умолчанию — последние два календарных месяца; часовой пояс — Москва. В интерфейсе можно изменить сотрудника, даты и пояс.

Скрипт читает данные портала и сохраняет отчёт локально. Методов изменения портала, подписки на события и отправки сообщений в нём нет.

## Запуск

Для окна с полями откройте `START_GUI.cmd` и следуйте `README_GUI_RU.txt`.
Сотрудника выберите в загруженном списке или введите его числовой ID.

Консольный вариант (123 — пример, замените на нужный ID):

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\bitrix24_employee_audit.ps1 -EmployeeId 123
```

Обычный консольный запуск без ID не начинает сбор. Для продолжения существующего
отчёта сотрудник берётся из manifest.json. В режиме `-SelfTest` используется
синтетический тестовый сотрудник, а не данные портала.

## Права вебхука

Для всех реализованных источников нужны scopes `main`, `task`, `crm`, `disk`, `timeman`, `telephony`, `bizproc`. `profile` проверяет владельца вебхука. Вебхук от администратора даёт более широкий доступ, но не гарантирует видимость каждого объекта и наличие старых журналов. Для телефонии также нужны права просмотра статистики звонков.

Если какого-то scope нет, источник будет отмечен как недоступный или частичный; остальные продолжат работу. Скрипт сам права и настройки портала не меняет. Недоступность журналов исправляется на стороне портала, а не повторными запросами.

## Что собирается

| Источник | События и сведения | Ограничение |
| --- | --- | --- |
| Event Log | Тип события, время, пользователь, модуль, объект, IP, URI, User-Agent, описание | Только реально сохранённые журналом события; зависит от тарифа и срока хранения |
| История задач | Создание, изменения полей и статуса, сроки, исполнители, комментарии, чек-листы, файлы, проекты, спринты, потоки; значения до/после | Автор определяется по `history.user.id`; задачи должны попасть в доступное перечисление |
| Трудозатраты | Записи от имени сотрудника, секунды, минуты, комментарий, источник, три исходные даты | Ручной учёт задним числом меняет смысл дат; запись не доказывает фактическую работу |
| CRM-дела | Создание и последнее изменение, автор и редактор, описание и дополнительные поля в JSON | Только последнее состояние, без промежуточных правок |
| CRM-объекты | Автор создания, последний редактор, последний автор смены стадии, последняя активность таймлайна | Последняя активность отмечена косвенным признаком: эти поля доступны для записи через API |
| CRM-комментарии | Автор, дата и текущий текст | Обход всех видимых элементов, включая чужие карточки; удалённые комментарии не восстановить |
| Логи приложений в CRM | Записи `crm.timeline.logmessage.list` от имени сотрудника | Только записи приложений, не системная история CRM |
| Диск | Создатель, последний редактор, перенос в корзину, время, имя, размер; обход вложенных папок | Только доступные метаданные; не все версии и не безвозвратно удалённые объекты |
| Контроль времени | Рабочие дни, перерывы, статусы «Отошёл», «Офлайн», события приложения при наличии детализации | Функция может быть выключена; часть данных доступна только руководителю |
| Рабочее время REST 3.0 | Начало и окончание интервалов учёта | Записи могут корректироваться; это не история всех корректировок |
| Телефония | Связанные с сотрудником звонки, время, тип, длительность, номер, код результата | Принадлежность записи сотруднику не означает успешный разговор; аудиофайлы не скачиваются |
| Шаблоны БП | Текущая структура, параметры, переменные, константы; пользователь и дата последнего создания/изменения | Дизайнерские шаблоны; шаблоны роботов стадий этим методом не выдаются |

CRM охватывает лиды, сделки, контакты, компании, предложения, новые счета и смарт-процессы, обнаруженные через `crm.type.list`.

Период применяется к событиям итоговой таблицы. Для поиска этих событий скрипт перечисляет родительские объекты независимо от их текущего ответственного и возраста. Иначе потеряются, например, сентябрьские комментарии в старой чужой сделке. Сырые страницы могут содержать объекты и даты за пределами периода и данные других пользователей; итоговая таблица фильтрует сотрудника и период.

На большом портале обход может быть долгим. Истории задач читаются пакетами до 25 задач, сначала по связям выбранного сотрудника, затем по всему доступному списку. Комментарии читаются по элементам CRM. Пауза между внешними запросами по умолчанию — 1000 мс. Оценку времени без количества объектов заранее дать нельзя.

## Результат

| Файл | Назначение |
| --- | --- |
| `timeline.html` | Основная таблица в браузере: дата, время, лог, действие, объект; поиск, подробности и ссылки на JSON |
| `timeline_employee_ID.csv` | Таблица для Excel: UTF-8 с BOM, разделитель `;` |
| `timeline_employee_ID.json` | Полная структурированная хронология без защитного экранирования CSV |
| `summary.json` | Период, число строк, ошибки, число запросов, ограничения и статусы источников |
| `status.json` | Состояние каждого источника, обновляется в ходе сбора |
| `collection_errors.json` | Ошибки текущего запуска |
| `rejected.json` | События, даты которых разобрать не удалось |
| `errors.ndjson`, `rejected.ndjson` | Накопительные журналы ошибок; сохраняются сразу, могут содержать ошибки предыдущих попыток |
| `manifest.json` | Зафиксированные параметры выгрузки; секрет вебхука не сохраняется |
| `raw/` | Сохранённые ответы вместе с методом, телом запроса и временем получения; успешные страницы служат checkpoint |

В CSV/HTML нет полного JSON в каждой строке: поле «Первоисточник» ведёт к файлу ответа. Известные URL вебхуков и распространённые query-токены в ответах и ошибках маскируются. Это не побайтовый архив HTTP: сохраняется структура JSON с маскированием известных секретов.

Дата отображается по Москве, сортировка идёт по UTC. Исходная дата и её смещение сохранены. Для дат без смещения по умолчанию предполагается Москва; если портал выдаёт локальные даты другого пояса, задайте `-InputTimeZoneId` при первом запуске.

Типы подтверждения помогают различать прямое событие, метаданные объекта и косвенный признак. Ответственный за задачу или CRM-дело сам по себе не считается автором изменений. Одно действие может подтверждаться несколькими источниками; такие независимые свидетельства сохраняются отдельно. Точные повторы одной исходной записи убираются.

Строки одного момента сортируются стабильно по ID, но это не доказывает последовательность действий внутри одной секунды.

## Как читать полноту

- `completed_with_limits`: обход доступных данных завершён с указанными ограничениями; ноль строк означает отсутствие найденных записей, а не доказательство отсутствия действий.
- `partial`: часть строк получена, но были ошибки.
- `failed_or_unavailable`: источник не дал строк и завершился с ошибкой или недоступен.
- `running` / `interrupted`: источник обрабатывается или работа прервана.

В `summary.json` поле `FullPortalHistoryConfirmed` всегда `false`: один успешный CSV не доказывает полноту истории портала. Каждый источник содержит собственное описание ограничений.

При штатно обработанной ошибке отчёт формируется из полученных данных. При Ctrl+C выполняется завершающая выгрузка, насколько это позволяет PowerShell; при закрытии окна или отключении питания окончательной таблицы может ещё не быть. Сохранённые страницы позволяют продолжить работу.

## Продолжение после остановки

Запустите из PowerShell, указав **тот же каталог**, который вывел первый запуск:

```powershell
.\bitrix24_employee_audit.ps1 -Resume -OutputDir 'C:\путь\к\Bitrix24_Audit_2052_...'
```

Скрипт снова запросит вебхук. Период и параметры прочитает из `manifest.json`. Уже сохранённые успешные запросы возьмёт с диска, недостающие выполнит. Поэтому повторный запуск не выгружает всё заново, хотя повторно обходит локальные checkpoint-файлы и строит общую таблицу.

Для пересборки только из имеющихся страниц, без вебхука и сетевых запросов:

```powershell
.\bitrix24_employee_audit.ps1 -RebuildOnly -OutputDir 'C:\путь\к\Bitrix24_Audit_2052_...'
```

Если страницы не хватает, будет отмечен пробел, сеть не используется. Для нового свежего аудита запускайте без `-Resume`, в новую папку. У API нет единого транзакционного снимка портала: данные могут меняться во время длительного обхода. Возобновление сохраняет ранее полученные страницы, а не обновляет их задним числом.

## Явный период или другой сотрудник

```powershell
.\bitrix24_employee_audit.ps1 -EmployeeId 2052 -From '2026-09-16T00:00:00+03:00' -To '2026-11-17T00:00:00+03:00'
```

Это пример фиксированных границ: `To` исключается, поэтому дата `2026-11-17T00:00:00+03:00` включает весь день 16 ноября. Обычный запуск без дат берёт ровно два календарных месяца до момента запуска. Будущие данные получить нельзя.

## Исправления относительно исходного файла

1. Event Log ограничен периодом и запрашивается окнами до суток. После временных ошибок/таймаутов окно делится вплоть до интервалов не более часа. Неполученные интервалы записываются в ошибки.
2. Checkpoint — отдельные атомарно сохранённые страницы. Ключ запроса стабилен между процессами PowerShell. Параметры и владелец вебхука проверяются по manifest; параллельная запись в одну папку блокируется.
3. Невалидная дата сохраняется отдельно и делает статус источника неполным; тихого удаления события нет.
4. Повторяются сетевые сбои, 429, временные серверные ошибки и лимиты API. Учитывается `Retry-After`; постоянные ошибки не повторяются. Ошибки REST 3.0 распознаются и при объекте `error`, и при HTTP 200. Ошибочные ответы не используются как успешный checkpoint.
5. Пагинация учитывает конкретный контракт: `next` для списков, `start` для истории и комментариев, `NAV_PARAMS` для трудозатрат, `pagination` и пустую завершающую страницу для REST 3.0. Повторяющаяся страница вызывает ошибку вместо бесконечного цикла.
6. Автор изменения задачи отделён от исполнителя. У CRM и Диска последнее состояние не выдаётся за всю историю. Смысл дат трудозатрат указан прямо в строках.
7. Расширен словарь истории задач. Неизвестные коды сохраняются как есть.
8. Время приведено к единой зоне. В PowerShell 6+ JSON читается без автоматического превращения ISO-строк в DateTime, чтобы не терять исходное смещение.
9. Добавлены статусы источников и HTML-таблица. Текст HTML экранируется; возможные формулы в CSV нейтрализуются, исходные значения остаются в JSON.
10. Обёртка над curl с временными файлами заменена штатным `Invoke-WebRequest -UseBasicParsing`. Сбор остаётся одним PowerShell-файлом без сторонних модулей и базы данных.

`crm.activity.list` оставлен в REST 2.0 осознанно: документация сохраняет этот вариант для полей, которых нет в REST 3.0. Это не утверждение о полной миграции на новую версию. Если портал перестанет принимать legacy-метод, источник явно получит ошибку; молчаливого переключения на другой контракт нет.

## Что восстановить этим скриптом нельзя

Полный журнал всех кликов, просмотров карточек и действий другого сотрудника в чатах через общий REST не выдаётся. Историю безвозвратно удалённых объектов, отсутствующие/очищенные журналы и промежуточные изменения метаданных восстановить нельзя.

REST-статистика вебхука/приложения сама по себе не доказывает, какой человек вызвал метод. Отдельный недокументированный метод персонального экспорта такой статистики здесь не выдумывается. События интеграций попадут в хронологию, если они есть в доступном Event Log с нужным userId.

Текущий шаблон БП не является историей изменения роботов, прав доступа и интеграций. Для доказательства конкретной настройки нужен подходящий журнал, заранее накопленная история событий либо снимки до/после. Скрипт таких доказательств задним числом не создаёт.

## Проверка

```powershell
.\bitrix24_employee_audit.ps1 -SelfTest
```

Используются только синтетические ответы внутри процесса, запросов к порталу нет. Проверяются период, UTC/московское время, сохранность исходного смещения JSON, дедупликация, авторство, комментарии в чужих карточках, позиционные параметры трудозатрат, пагинация, checkpoint и все сборщики. Тестовый отчёт помещается в отдельную временную папку и помечается `SelfTest: true` в manifest.

При подготовке выполнены проверки в **PowerShell 7.4.13 на Linux**, включая запуск нового процесса с `-Resume` и `-RebuildOnly` (ноль сетевых запросов), а также проверки временных ошибок, `Retry-After`, HTTP 401, ошибок REST 3.0, повторяющихся страниц и частичного результата. Дополнительно выполнены проверки на настоящем Windows PowerShell 5.1 через GitHub Actions: дочерний процесс, WPF-окно, список сотрудников, отмена, история и пакетное чтение, реальные HTTP 400/401/429 тестового сервера. Живой запуск на вашем портале не выполнялся: нужен ваш локальный вебхук.

## Дополнение для графического интерфейса

Параметр `-CancelFile` используется приложением для согласованной остановки. При появлении этого файла сборщик завершает текущую операцию, формирует частичный отчёт в `finally` и освобождает блокировку. Для загрузки справочника сотрудников окно использует `user.get` с scope `user`, `user_basic` или `user_brief`; личные данные, не нужные для выбора, не запрашиваются.


## Версия 1.1.0
Общий транспорт находится в обязательном файле `bitrix24_http.ps1` и использует штатный .NET HttpClient. HTTP-ответ читается независимо от статуса. JSON, пояснения валидации и текстовые ошибки сохраняются в raw. Даты Event Log передаются без дробных секунд. При HTTP400 применяется один резервный обход по userId с локальной фильтрацией периода; в summary это отмечается `EventLogLocalDateFilter`. Постоянные отказы останавливают источник. Реальная причина прежнего 401 без тела ответа неизвестна; приложение не обходит права доступа.


Версия 1.2.0 — ограничения API
HTTP429 и RATELIMITEXCEPTION откладывают источник сразу; оставшиеся источники продолжают сбор. После первого обхода выполняется не более одного повторного обхода отложенных источников. При отсутствии Retry-After используется пауза 5 минут; при наличии заголовка приложение не обращается к методу раньше указанного срока. Ожидание перед финальными повторами ограничено общим бюджетом 5 минут. Если требуется больше, формируется частичный отчёт, источник остаётся отложенным: повторите через режим продолжения позднее.
Пауза по умолчанию — 1000 мс. Отсчёт ожидания виден в журнале и в окне; остановка доступна каждую секунду. SQL-таймаут REST3 не повторяет тяжёлый запрос четыре раза перед уменьшением интервала. Блокировку сервера приложение не обходит.
rate_limits.json сохраняет сроки блокировки методов для продолжения. summary.Errors отражает ошибки итоговых статусов, ErrorHistoryCount — все ошибки попыток, в том числе восстановленных источников.
Для проверки без портала запустите TEST_RATE_LIMITS.ps1 в PowerShell. Тест проверяет 429, переход к другим источникам, Retry-After, повтор и остановку без реального ожидания 5 минут.


Версия 1.3.0 — проверка фактических прав и видимое продвижение
Перед обходом вызывается scope без full:true, сохраняется access_check.json с фактическими правами, доменом, владельцем и отсутствующими кодами. Для задач требуется именно task, а не tasks. При выданном task выполняется проба первой страницы tasks.task.list до долгого обхода. Источники без требуемого scope не запрашиваются; приложение не может выдать токену недостающие права.
В 1.6.0 Event Log выполняется перед задачами; задачи обрабатываются последними. Сначала собираются CRM-дела и другие более быстрые источники; полный обход комментариев CRM остаётся длительным на большом портале и показывает текущие вызовы и счётчик событий. После каждого источника сохраняются промежуточные HTML/CSV/JSON. До завершения процесса это частичный результат.
TEST_ACCESS.ps1 проверяет свежесть scope, различие task/tasks, пропуск недоступного источника, продолжение доступного и промежуточный отчёт.
Если права менялись в настройках, сохраните вебхук и заново скопируйте адрес именно отредактированного вебхука. Выполнение scope с full:true показывает все права портала и не доказывает их наличие у используемого токена.
Документация: https://apidocs.bitrix24.ru/api-reference/common/system/scope.html и https://apidocs.bitrix24.ru/api-reference/tasks/tasks-task-list.html


Версия 1.4.0 — результаты и объяснение отбора
История tasks.task.history.list читается одним ответом без выдуманного start. Если сервер явно возвращает next, используется только этот указатель. Массив из 50, 130 или большего количества записей сам по себе не является признаком следующей страницы. Это устраняет ошибочные повторные запросы при получении полной истории.
Задачи читаются от недавно изменённых к старым, без исключения старых задач или задач других ответственных.
diagnosis.json и раздел «Почему найдены именно эти события» в HTML показывают количество прочитанных уникальных записей истории, нераспознанных авторов и дат, записей выбранного сотрудника, попаданий в период и записей вне периода; диапазон прочитанных дат и число записей по ID авторов. Число HTTP-запросов не считается числом действий сотрудника. Диагноз относится только к прочитанной части, а не к неизвестной истории всего портала.
Для локального разбора уже загруженных ответов выберите в окне «Пересобрать сохранённый отчёт без интернета» и старую папку с manifest.json. Первые страницы истории старых версий совместимы с новым читателем. Уже сохранённые JSON повторно не запрашиваются; отсутствующие страницы отмечаются как пробелы. Полное повторное скачивание не требуется.
TEST_HISTORY.ps1 проверяет один ответ со 130 событиями, отбор по автору и периоду, дубликаты, неразобранные даты, частичный диагноз и повторное использование старого кэша без сети.
Повторный разбор не создаёт отсутствующие данные. Для новых данных используйте продолжение сбора; для свежего снимка — новый отчёт. Клики, просмотры и недоступная административная история не восстанавливаются через историю задач.
Документация: https://apidocs.bitrix24.ru/api-reference/tasks/tasks-task-history-list.html

## Версия 1.5.0 — скорость и проверка запуска

Истории задач загружаются через штатный REST `batch` пакетами до 25 задач. Каждая успешная история сохраняется отдельно и сразу доступна для продолжения/пересборки. Ошибка одного ответа не уничтожает соседние: неуспешные истории проверяются отдельными запросами. Если batch недоступен, применяется обычное чтение.

Сначала проверяются задачи, где выбранный сотрудник — постановщик, исполнитель, автор последнего изменения статуса, соисполнитель или наблюдатель. Затем выполняется общий обход всех доступных задач с устранением повторов. Связь с задачей определяет приоритет, а действие в отчёт попадает только после проверки автора и даты. Нет ограничения только назначенными на сотрудника задачами.

Дочерний процесс выводит обычный UTF-8 текст вместо CLIXML. Служебные сообщения загрузки модулей отключены до первой команды. `TEST_BATCH.ps1` проверяет приоритеты и полный обход, 100 историй за четыре HTTP-запроса, сохранение отдельных историй, продолжение без сети и восстановление после ошибки внутри пакета.

Автоматизация Windows: `.github/workflows/bitrix24-audit-tests.yml` запускает проверки на Windows PowerShell 5.1, создаёт настоящее WPF-окно через `-UiSmokeTest` и сохраняет его изображение. Подключение к реальному порталу требует введённого локально вебхука и не является частью синтетических тестов.

Windows PowerShell 5.1: исправлена нормализация JSON-массивов списка сотрудников.
Промежуточный отчёт обновляется после страниц задач без изменения статуса выполняемого источника на «Остановлен».
Проверки Windows: https://github.com/samogt/jdnsd/actions/workflows/bitrix24-audit-tests.yml

ВЕРСИЯ 1.6.0 — УПРАВЛЕНИЕ ДЛИТЕЛЬНЫМ ОБХОДОМ
Остальные источники выполняются до этапа «Задачи». История и трудозатраты читаются за один проход по задачам. Общая проба tasks.task.list при проверке доступа убрана.
«Открыть текущий отчёт» доступно во время сбора после первого сохранения таблицы.
«Пропустить этот источник» прерывает только текущий этап, сохраняет данные и продолжает остальные. При этом итог помечается как частичный, даже если технических ошибок нет.
«Остановить и сохранить» завершает весь сбор с частичным отчётом. Ожидающий HTTP-запрос прерывается, а не ожидает 90-секундного таймаута. Намеренный пропуск не повторяется автоматически в текущем запуске.
Для недостающих данных выберите продолжение и ту же папку: успешные страницы не скачиваются заново. Сотрудник и период берутся из прежнего manifest.json.
В окне показываются проверенные задачи, общее число (если известно), записи истории и длительность ожидания текущего запроса. Срок ожидания увеличивается даже без новых строк журнала. Эти показатели также есть в run_state.json.
Новые проверки: TEST_LARGE_PORTAL.ps1 (10000 задач, 8000 записей чужого автора), TEST_CONTROLS.ps1 (пропуск и таймер), TEST_HTTP.py (остановка и пропуск во время реального задержанного HTTP-запроса).
