# Битрикс24: хронология сотрудника — 1.6.0

**[Скачать приложение для Windows — ZIP](https://github.com/samogt/jdnsd/raw/refs/heads/main/bitrix24-audit/bitrix24_gui.zip)** · [Проверки Windows](https://github.com/samogt/jdnsd/actions/workflows/bitrix24-audit-tests.yml)

Распакуйте весь архив в отдельную папку и запустите **START_GUI.cmd**. Введите вебхук, загрузите список сотрудников и выберите человека. По умолчанию сотрудник не выбран; период — последние два календарных месяца. Укажите папку и нажмите **«Сформировать отчёт»**. Приложение показывает три последовательных шага: параметры → формирование → результат.

На выходе — `timeline.html` с поиском и таблицей **дата, время, лог, действие в Битрикс24, объект, автор, подтверждение**, CSV для Excel и JSON. Каждая строка ссылается на сохранённый ответ API. Причины отсутствия данных и статусы источников входят в отчёт; число запросов не выдаётся за число действий.

Приложение работает локально в Windows PowerShell 5.1 с WPF. Сервер, Python, Node.js и сторонние модули для запуска не нужны. Вебхук вводится только локально. В репозитории нет рабочего вебхука или выгрузок портала. Сборщик использует методы чтения и не меняет данные портала.

## Изменения 1.6.0

Причина долгого ожидания: версия 1.5.0 обходила все доступные задачи до Диска, комментариев CRM и Event Log. Период применялся к событиям после чтения историй и не ограничивал число родительских задач.

Теперь остальные источники выполняются раньше, а история задач и трудозатраты читаются за один общий обход в последнем этапе «Задачи». Предварительный общий запрос задач из проверки доступа убран. Полный поиск по чужим и старым задачам сохранён, поэтому действия в них не исключаются молча.

Во время сбора доступны **«Открыть текущий отчёт»**, **«Пропустить этот источник»** и **«Остановить и сохранить»**. Пропуск относится только к показанному этапу; другой источник случайно пропущен не будет. Пропуск и общая остановка прерывают ожидающий HTTP-запрос. Отчёт показывает неполный охват после пропуска и остаётся пригодным для продолжения по сохранённым страницам.

Окно показывает проверенные задачи, общее число доступных задач (когда портал его вернул), прочитанные записи истории и живой счётчик ожидания ответа API. `run_state.json` хранит эти показатели без вебхука.

## Сохранённые исправления

- Истории задач читаются через штатный `batch` пакетами до 25 задач. Успешные ответы сохраняются отдельно; ошибки внутри пакета повторяются отдельными запросами. При недоступности batch остаётся обычное чтение.
- Сначала обрабатываются задачи, связанные с выбранным сотрудником, затем все остальные доступные задачи. Повторы исключаются. В итог попадают события с подходящими автором и датой, включая события в чужих задачах.
- История задачи из 130 записей принимается целиком. Следующая страница запрашивается только при явном `next` от сервера.
- Исправлено чтение JSON-массивов списка сотрудников в Windows PowerShell 5.1. Дочерний процесс выдаёт обычный UTF-8 текст вместо CLIXML.
- Промежуточный отчёт обновляется после страниц задач и каждого источника. Остановка сохраняет частичный результат, продолжение использует загруженные страницы. Есть пересборка без интернета.
- HTTP 400/401 сохраняют настоящий ответ сервера. HTTP 429 откладывает источник с учётом Retry-After; остальные источники продолжают работу. Источники без выданного scope не запрашиваются. Event Log обрабатывается перед финальным этапом задач.

## Права и доступные данные

Для списка сотрудников нужен один из scopes `user`, `user_basic`, `user_brief`. Для всех источников: `main`, `task`, `crm`, `disk`, `timeman`, `telephony`, `bizproc`. Проверяется фактический `scope` вебхука без `full:true`. Право `task` не заменяется похожими `tasks_extended` или `tasksmobile`.

Собираются доступные Event Log, история задач, трудозатраты, CRM-дела, метаданные CRM, комментарии и логи приложений CRM, метаданные Диска, рабочее время, телефония и метаданные шаблонов бизнес-процессов. Точный состав и ограничения описаны в [документации сборщика](README_COLLECTOR_RU.md).

Полный обход большого портала может быть длительным. Права владельца вебхука, тариф и сроки хранения ограничивают доступ. Метаданные отражают текущее или последнее состояние; отсутствующая история, просмотры и клики не восстанавливаются. Частичный результат явно отмечается. `diagnosis.json` показывает, сколько записей истории прочитано, сколько принадлежат сотруднику и сколько попадают в период.

## Проверка

`TEST_LARGE_PORTAL.ps1`: портал с 10000 задачами, 8000 прочитанными записями другого автора и нулём совпадений с сотрудником. Проверяется завершение всех восьми остальных источников до обхода задач, чтение трудозатрат в том же проходе, пропуск с сохранением полезного отчёта, явный частичный статус и защита следующего источника от старого запроса пропуска.

`TEST_HTTP.py`: настоящий локальный HTTP-сервер задерживает ответ на 15 секунд. Проверяется прерывание уже отправленных запросов при остановке и пропуске быстрее пяти секунд, без повторных запросов. `TEST_CONTROLS.ps1` проверяет смену источника, запрос пропуска и таймер ожидания без новых строк журнала. В Windows `-UiSmokeTest` также запускает сборщик и доводит настоящее окно до экрана результата с 65 тестовыми событиями.

Автоматические проверки выполнены на настоящем Windows PowerShell 5.1: запуск дочернего процесса, выбор сотрудника и список пользователей, создание WPF-окна, отмена, продолжение, авторы и даты, 130 записей одним ответом, 100 историй за четыре пакетных HTTP-запроса, восстановление отдельных ошибок пакета, реальные тестовые HTTP 400/401/429. Изображение окна сохраняется в артефактах Windows-проверки. Проверки используют синтетические данные и локальный HTTP-сервер; подключения к пользовательскому порталу в них нет.

Инструкция: [README_GUI_RU.txt](README_GUI_RU.txt). Для обновления распакуйте весь новый архив отдельно; старые папки результатов сохраняйте и выбирайте в режиме продолжения или пересборки.
