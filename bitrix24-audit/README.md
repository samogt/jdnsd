# Битрикс24: отчёт по выбранному сотруднику — 1.3.0

**[Скачать приложение для Windows — ZIP](https://github.com/samogt/jdnsd/raw/refs/heads/main/bitrix24-audit/bitrix24_gui.zip)**

1. Скачайте и полностью распакуйте архив.
2. Дважды нажмите **START_GUI.cmd**.
3. Введите вебхук, загрузите список и выберите сотрудника. По умолчанию никто не выбран; можно явно ввести ID.
4. Укажите период и папку, нажмите **«Сформировать отчёт»**.
5. Получите результат и откройте таблицу или CSV для Excel.

Приложение последовательно показывает **параметры → формирование → результат**. По умолчанию выбран период последних двух календарных месяцев. Готовый отчёт содержит дату, время, действие, объект, подтверждение и ссылки на сохранённые JSON-ответы.

Работает локально в Windows с Windows PowerShell 5.1 и WPF. Устанавливать сервер, Python, Node.js или сторонние модули не нужно. Вебхук вводится в приложении; в архиве нет рабочих токенов и выгрузок портала.

- [Подробная инструкция по интерфейсу](README_GUI_RU.txt)
- [Источники данных, права, ограничения и документация сборщика](README_COLLECTOR_RU.md)

Для списка сотрудников нужен один из scopes `user`, `user_basic`, `user_brief`. Для всех источников сбора: `main`, `task`, `crm`, `disk`, `timeman`, `telephony`, `bizproc`. Доступность данных зависит от прав владельца вебхука, тарифа и сохранности журналов.

Поддерживаются остановка с частичным отчётом, продолжение по сохранённым страницам и пересборка без сети. Сборщик использует методы чтения; настройки и данные портала не изменяет.

Логика проверена в PowerShell 7.4.13 на Linux на синтетических данных, включая запуск дочернего процесса, выбор сотрудника, пагинацию, остановку и восстановление. Фактическое отображение WPF-окна на Windows и подключение к пользовательскому порталу в этой среде не проверялись.

## Исправления 1.1.0

Исправлена потеря тела HTTP400/401 в Windows PowerShell. Запросы выполняет штатный .NET HttpClient из обязательного файла `bitrix24_http.ps1`. Даты Event Log отправляются без дробной части; при отклонении фильтра дат выполняется один резервный обход событий сотрудника с локальным отбором периода. Постоянные отказы не повторяются по всем дням. При нуле событий и ошибках приложение явно сообщает о неудаче.

Распакуйте **весь** новый архив в отдельную папку. Фактическая причина прежнего HTTP401 неизвестна: старый журнал не содержал ответа API. Неверный токен или недостаточные права приложение не может исправить вместо администратора. Подключение к вашему порталу не проверялось. Реальные ответы 400/401 проверены на локальном HTTP-сервере; сценарии GUI проверены на синтетических данных.


Версия 1.2.0 — ограничения API
HTTP429 и RATELIMITEXCEPTION откладывают источник сразу; оставшиеся источники продолжают сбор. После первого обхода выполняется не более одного повторного обхода отложенных источников. При отсутствии Retry-After используется пауза 5 минут; при наличии заголовка приложение не обращается к методу раньше указанного срока. Ожидание перед финальными повторами ограничено общим бюджетом 5 минут. Если требуется больше, формируется частичный отчёт, источник остаётся отложенным: повторите через режим продолжения позднее.
Пауза по умолчанию — 1000 мс. Отсчёт ожидания виден в журнале и в окне; остановка доступна каждую секунду. SQL-таймаут REST3 не повторяет тяжёлый запрос четыре раза перед уменьшением интервала. Блокировку сервера приложение не обходит.
rate_limits.json сохраняет сроки блокировки методов для продолжения. summary.Errors отражает ошибки итоговых статусов, ErrorHistoryCount — все ошибки попыток, в том числе восстановленных источников.
Для проверки без портала запустите TEST_RATE_LIMITS.ps1 в PowerShell. Тест проверяет 429, переход к другим источникам, Retry-After, повтор и остановку без реального ожидания 5 минут.


Версия 1.3.0 — проверка фактических прав и видимое продвижение
Перед обходом вызывается scope без full:true, сохраняется access_check.json с фактическими правами, доменом, владельцем и отсутствующими кодами. Для задач требуется именно task, а не tasks. При выданном task выполняется проба первой страницы tasks.task.list до долгого обхода. Источники без требуемого scope не запрашиваются; приложение не может выдать токену недостающие права.
Event Log выполняется последним. Сначала собираются CRM-дела и другие более быстрые источники; полный обход комментариев CRM остаётся длительным на большом портале и показывает текущие вызовы и счётчик событий. После каждого источника сохраняются промежуточные HTML/CSV/JSON. До завершения процесса это частичный результат.
TEST_ACCESS.ps1 проверяет свежесть scope, различие task/tasks, пропуск недоступного источника, продолжение доступного и промежуточный отчёт.
Если права менялись в настройках, сохраните вебхук и заново скопируйте адрес именно отредактированного вебхука. Выполнение scope с full:true показывает все права портала и не доказывает их наличие у используемого токена.
Документация: https://apidocs.bitrix24.ru/api-reference/common/system/scope.html и https://apidocs.bitrix24.ru/api-reference/tasks/tasks-task-list.html
